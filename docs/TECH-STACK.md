# 技术栈选型方案

> 结论先行：**玩法验证期用「原生 TS + Canvas」（已完成，见 `games/jump/src/`）；产能瓶颈出现后再评估迁移 Cocos Creator 3.x。**
> 核心逻辑层 `games/jump/src/core/` 与引擎无关，迁移时不用重写。

---

## 一、对比总览

| 维度 | Cocos Creator 3.x | 原生 TS + Canvas |
|---|---|---|
| 包体大小 | 较大（引擎运行时通常数 MB 级） | 极小（本项目 12KB，压缩后个位数 KB） |
| 启动速度 | 需要引擎初始化，首屏偏慢 | 几乎瞬时 |
| 开发效率（简单 2D） | 中（要学编辑器、组件体系） | 高（纯代码，改完即见） |
| 开发效率（复杂美术） | 高（编辑器直接拖拽、时间轴动画） | 低（全靠手写渲染代码） |
| 动画 / 粒子 / 骨骼 | 内置且成熟 | 需手写或引第三方库 |
| 物理引擎 | 内置 Box2D / 物理系统 | 需自己实现（本项目跳跃用了参数化抛物线） |
| 抖音小游戏适配 | 官方构建目标，一键出包 | 用 `tt.*` API，自己写适配层（本项目已封装） |
| 学习曲线 | 陡（编辑器 + 引擎概念） | 平缓（会 JS/TS 即可） |
| 多人协作 | 场景文件易冲突但分工清晰 | 代码冲突好解决，但美术资源需自行组织 |
| 长期维护 | 引擎大版本升级有迁移成本 | 代码全在自己手里，无外部依赖风险 |
| 广告 / 平台 API | 都是调 `tt.*`，**无明显差异** | 同左 |

---

## 二、Cocos Creator 3.x

**优点**

1. **抖音官方支持**：Creator 构建面板有「抖音小游戏」目标，一键出包，适配由引擎保证。
2. **可视化**：场景、UI、预制体拖拽摆放，动画用时间轴做，改美术不用改代码。
3. **能力齐全**：粒子系统、Spine/龙骨骨骼动画、Tween、物理引擎、UI 布局开箱即用。
4. **资源管线**：图集打包、分包加载、远程资源（CDN）都有现成方案，包体超限时能平滑处理。
5. **团队可扩展**：策划/美术可以独立操作编辑器，不依赖程序员。

**缺点**

1. **包体大、启动慢**：引擎运行时占体积，冷启动耗时会直接吃掉「3 秒内可玩」的窗口，对抖音这种刷视频滑进来的场景是实打实的留存损失。
2. **学习曲线陡**：不熟引擎时，一个简单玩法也要先花几天搭工程、理解生命周期。
3. **黑盒依赖**：引擎升级、构建坑、真机兼容问题要等官方修，自己改不动。
4. **对极简玩法是过度设计**：本项目这种「一个方块在平台上跳」的玩法，用引擎 90% 的功能用不上。

**适用**

- 美术/动画量大、需要粒子特效和骨骼动画的项目；
- 3D 项目；
- 需要多人协作、策划/美术参与编辑的项目；
- 已经熟练 Cocos 的团队。

**不适用**

- 极简休闲、追求极致启动速度的项目；
- 一个人、要快速验证玩法行不行的情况。

## 三、原生 TS + Canvas（当前方案）

> 关于构建工具：**没有用 Vite，用的是 esbuild。**
> 原因：Vite 产出的是 ESM 多文件 + 依赖浏览器模块加载，抖音小游戏运行时不走浏览器 `import`；esbuild 可直接产出**单文件 IIFE**，丢进 `game.js` 就能跑，且构建只要几毫秒。浏览器预览用的是 esbuild 自带的 dev server。

**优点**

1. **包体极小、启动极快**：本项目 `games/jump/dist/game/game.js` 仅 12KB（压缩后），冷启动基本无感。
2. **逻辑完全可控**：没有任何黑盒。跳跃手感、落点判定、难度曲线全都写在 `games/jump/src/core/`，可以单元测试（本项目 11 个测试全部覆盖核心规则）。
3. **改一行立刻见效**：调手感不用等编辑器重新构建。
4. **零运行时依赖**：不会被引擎版本升级绑架。
5. **逻辑与渲染解耦**：`games/jump/src/core/game.ts` 是纯函数式状态机，不碰 canvas，可以在 Node 里跑测试、以后迁到任何引擎。

**缺点**

1. **美术管线要自己搭**：图集、序列帧、骨骼动画都得手写或引第三方库。
2. **没有可视化编辑**：界面位置靠代码写，改 UI 要改代码。
3. **复杂玩法成本高**：一旦涉及物理碰撞、寻路、粒子特效，自己实现的成本会快速超过「学引擎」的成本。
4. **靠个人工程质量**：架构、性能优化全靠自己把关。

**适用**

- 极简 2D 休闲玩法（跳跃、躲避、消除、答题、点按类）；
- 追求启动速度和包体；
- 单人/小团队快速验证玩法；
- 需要大量逻辑单元测试的场景。

**不适用**

- 美术资源多、动画复杂的项目；
- 3D；
- 玩法强依赖物理引擎。

## 四、决策依据（为什么现在选原生）

| 判断标准 | 本项目现状 | 倾向 |
|---|---|---|
| 玩法复杂度 | 一维跳跃 + 落点判定 | 原生 |
| 美术资源量 | 目前为纯色块 + 代码绘制 | 原生 |
| 启动速度敏感度 | 抖音刷视频进入，极高 | 原生 |
| 是否需要单元测试 | 需要验证可达性/复活/计分 | 原生 |
| 团队人数 | 1 人 | 原生 |

**迁移触发信号（任一出现就重新评估 Cocos）**

1. 美术资源需要序列帧之外的表现（骨骼动画、粒子、Shader 特效）；
2. 玩法需要真实物理碰撞（多物体刚体）；
3. 要做 3D 或伪 3D 视觉；
4. 有策划/美术要独立改内容，不能接受「改 UI 就找程序」。

**迁移成本可控的原因**

```
games/jump/src/core/       ← 纯逻辑，与引擎无关，直接复用
games/jump/src/platform/   ← tt API 封装，可直接复用
games/jump/src/render/     ← 唯一需要重写的层
```

迁移时只重写渲染层，玩法规则、存档、广告逻辑全部搬过去。

---

## 五、一句话总结

- **验证玩法、抢启动速度 → 原生 TS + Canvas（现在）**
- **做内容、堆美术、上量 → Cocos Creator 3.x（以后）**
- 两者不是对立关系，本项目已经用「逻辑 / 渲染 / 平台」三层解耦，换引擎是重写一层，不是重写全部。
